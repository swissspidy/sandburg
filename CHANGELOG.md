# sandburg

## 0.3.0

### Minor Changes

- [#55](https://github.com/swissspidy/sandburg/pull/55) [`3217fd9`](https://github.com/swissspidy/sandburg/commit/3217fd99f6313b2f4c97e8fcbf55beea4483e58c) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster batches that use less memory. A batch starts its projects in the order earlier batches suggest (the summaries in its batch directory): new projects first, then those whose checks waited longest, then those that ran longest, so that the apps that keep a batch open no longer start last (results stay in the order given; `longestFirst: false` keeps the order). Before it opens another app, a batch checks that the machine (or the process's memory cgroup) has 1.5 GB available, and waits for an app to end when it has not (`memoryReserve`). `--parallel` and `runBatch` default to one app per core, up to 8, instead of 4. Batch summaries record each run's `checksMs`. The host's compiles in memory are bounded by their size (128 M characters) instead of their count.

- [#85](https://github.com/swissspidy/sandburg/pull/85) [`8da2982`](https://github.com/swissspidy/sandburg/commit/8da2982d7671789880e8189c94e8a2e052882bf3) Thanks [@swissspidy](https://github.com/swissspidy)! - Chromium now runs inside its OS sandbox by default, with every site in a renderer process of its own (`--site-per-process`). Before, Playwright's default launched it with `--no-sandbox`. Where the sandbox cannot start (as root, or where user namespaces are restricted, as AppArmor does on Ubuntu 23.10 and later), `Session.open()` fails with what to change. Sandburg does not fall back to an unsandboxed browser by itself; `--no-browser-sandbox`, `SANDBURG_NO_BROWSER_SANDBOX=1` or `browserSandbox: false` turns the sandbox off explicitly. Each run's `result.json` records the choice (`environment.browserSandbox`), as does a batch's `summary.json` (`browserSandbox`), and the CLI warns when the sandbox is off. Playwright's `--enable-unsafe-swiftshader` switch is left out: the headless shell runs WebGL without it.

- [#41](https://github.com/swissspidy/sandburg/pull/41) [`ec5b71c`](https://github.com/swissspidy/sandburg/commit/ec5b71cdec02721d3a252e59f6f4276e54730525) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster cold runs. For an install that was never run, the host transforms ahead the modules its programs will require, from the program's entry and each file the runtime asks for, and sends them as the first preload bundle. The host's install starts while the tab loads, the runtime's bundle is built while npm installs, WebAssembly builds and bindings are added side by side, and transforms of installed files are kept in memory. A Next.js app without a seed for its versions no longer waits for the seed run, which runs beside it; `Session.close` waits for a seed run in progress.

- [#49](https://github.com/swissspidy/sandburg/pull/49) [`dc60ecb`](https://github.com/swissspidy/sandburg/commit/dc60ecb55c4dd3aeb9ffe5e7b0e2380216da0342) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster runs of meta-framework apps (SvelteKit, Astro, Nuxt, SolidStart, React Router, Angular), warm ones above all. A run keeps its dev server's whole cache for the next run of the project (`node_modules/.vite` with SSR and plugin metadata, Nuxt's `node_modules/.cache/vite`, the Angular CLI's `.angular/cache`), sent to the runtime as a bundle, and the host keeps what it compiled for the project's runtimes (Vite's SSR modules) for its next run. The browser runtime starts `react-router dev` with `--conditions=development` (instead of relaunching it), `nuxt dev` with `--no-fork`, the Angular CLI with `NG_BUILD_PARALLEL_TS=0`, and napi-rs WebAssembly packages with one async worker (`NAPI_RS_ASYNC_WORK_POOL_SIZE=1`). The runtime takes node options (`execArgv`) for the program it starts.

- [#39](https://github.com/swissspidy/sandburg/pull/39) [`d8ddbf8`](https://github.com/swissspidy/sandburg/commit/d8ddbf8d51cbd9fe68e47ca2a8b8598f43273502) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster runs, warm ones above all. - [#109](https://github.com/swissspidy/sandburg/pull/109) [`eab706e`](https://github.com/swissspidy/sandburg/commit/eab706e6b2cefebcdfd740ad7f3209694edd297d) Thanks [@swissspidy](https://github.com/swissspidy)! - Fixes for the false alarms and slow diagnoses of fidelity study v7 ([ADR 0066](https://github.com/swissspidy/sandburg/blob/main/docs/adr/0066-fidelity-v7-fixes.md)):
  
  - An app that renders only into a custom element's shadow root (a Lit app) is ready once its open shadow roots show text; it timed out before.
  - The functional checks wait for a SolidStart page to hydrate (every server-rendered element claimed), up to 10 s: a `fill()` before then was lost. A framework that says it has not hydrated yet is waited for up to 10 s, others up to 3 s as before.
  - The ready phase fails fast on an error the app reports while its page never finishes loading (Angular's dev server after its dependency optimizer crashed), and on a page that answers 500 after a 503 loading page (Nuxt), instead of waiting out its deadline.
  - New classification: `server-render-error` (app-bug) for a page the dev server could not render on the server (Nuxt's request error, an error with a stack through the project's files in Astro's output); `compile-error` for Nuxt's `SyntaxError [VITE_ERROR]`; `app-error-before-ready` for an error the app logged instead of throwing, with a stack through its own code (Angular's ErrorHandler, SolidStart); `signature:wasm-trap` for a WebAssembly trap Vite reported to the page. `ClassifyInput` takes `readyOutputFrom` and `appPath` (optional): a server render error is the dev server's report on the app's page, since the ready phase began.

- [#111](https://github.com/swissspidy/sandburg/pull/111) [`32cfe97`](https://github.com/swissspidy/sandburg/commit/32cfe97e0b953e0b293fbf4bec2f33cfc5271152) Thanks [@swissspidy](https://github.com/swissspidy)! - The Node runtime handles uncaught exceptions and unhandled rejections as Node 24 does:
  
  - A top-level throw reaches `'uncaughtException'` listeners and the program goes on.
  - Without a listener, `'exit'` listeners run with code 1.
  - `'uncaughtExceptionMonitor'` and `process.setUncaughtExceptionCaptureCallback` work.
  - A throw in a listener exits with code 7.
