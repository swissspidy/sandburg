# sandburg

## 0.3.0

### Minor Changes

- [#41](https://github.com/swissspidy/sandburg/pull/41) [`ec5b71c`](https://github.com/swissspidy/sandburg/commit/ec5b71cdec02721d3a252e59f6f4276e54730525) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster cold runs. For an install that was never run, the host transforms ahead the modules its programs will require, from the program's entry and each file the runtime asks for, and sends them as the first preload bundle. The host's install starts while the tab loads, the runtime's bundle is built while npm installs, WebAssembly builds and bindings are added side by side, and transforms of installed files are kept in memory. A Next.js app without a seed for its versions no longer waits for the seed run, which runs beside it; `Session.close` waits for a seed run in progress.

- [#49](https://github.com/swissspidy/sandburg/pull/49) [`dc60ecb`](https://github.com/swissspidy/sandburg/commit/dc60ecb55c4dd3aeb9ffe5e7b0e2380216da0342) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster runs of meta-framework apps (SvelteKit, Astro, Nuxt, SolidStart, React Router, Angular), warm ones above all. A run keeps its dev server's whole cache for the next run of the project (`node_modules/.vite` with SSR and plugin metadata, Nuxt's `node_modules/.cache/vite`, the Angular CLI's `.angular/cache`), sent to the runtime as a bundle, and the host keeps what it compiled for the project's runtimes (Vite's SSR modules) for its next run. The browser runtime starts `react-router dev` with `--conditions=development` (instead of relaunching it), `nuxt dev` with `--no-fork`, the Angular CLI with `NG_BUILD_PARALLEL_TS=0`, and napi-rs WebAssembly packages with one async worker (`NAPI_RS_ASYNC_WORK_POOL_SIZE=1`). The runtime takes node options (`execArgv`) for the program it starts.

- [#39](https://github.com/swissspidy/sandburg/pull/39) [`d8ddbf8`](https://github.com/swissspidy/sandburg/commit/d8ddbf8d51cbd9fe68e47ca2a8b8598f43273502) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster runs, warm ones above all. Large compiled code is asked for by its digest before it is sent (`GET /__sandburg/compiled/<sha256>`), code goes to the host compiler as a Blob, preload bundles are built when their URL is issued, hold installed files up to 10 MB and name larger ones for the runtime to download on the side, base64 is native where the browser has it, and the Next.js 16 seed keeps webpack's cache from `.next/dev/cache`, where Next.js 16 writes it. A `.js` file with ES module syntax in a `"type": "commonjs"` scope now fails as it does in Node, instead of loading as a module.

- [#37](https://github.com/swissspidy/sandburg/pull/37) [`dd6a951`](https://github.com/swissspidy/sandburg/commit/dd6a951b9ed5c5f829c3d0ef83f479ca76b4d489) Thanks [@swissspidy](https://github.com/swissspidy)! - Next.js apps on TypeScript 7 run in the browser runtime. TypeScript 7's `tsc` is native code: in the runtime, `tsc --showConfig` (what `next dev` asks for) is answered in JavaScript, and type checks run tsrs, a Rust port of TypeScript 7, as WebAssembly (`@tsrs/wasm`). An extensionless module in `node_modules`, such as a package's `bin` script, now loads as JavaScript, as Node loads it.

### Patch Changes

- [#47](https://github.com/swissspidy/sandburg/pull/47) [`6542ef6`](https://github.com/swissspidy/sandburg/commit/6542ef677e029991bd748c9516bc01bd7260d64d) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster runs around the app: a session keeps the next run's tab ready (its context, host page and runtime loaded ahead of the run; `spareTab: false` turns it off), the checks load axe-core and the page checks' runtime off the main thread while the screenshot and accessibility snapshot are taken side by side, ready asks the host page whether the app rendered, and batches start the next app when one reaches its checks (at most twice `parallel` open).

- [#52](https://github.com/swissspidy/sandburg/pull/52) [`1121872`](https://github.com/swissspidy/sandburg/commit/1121872f453c46053b2efed5e2fb64b25d818e50) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster checks: the functional checks start once the app can take input (a server-rendered app that hydrates is waited for beside the screenshot, accessibility snapshot and axe-core, at most 3 s; Solid, React and Nuxt say when input is safe), a web-first assertion that waits is checked every 100 ms beside Playwright's own polls and passes as soon as the page gets there (failures and their messages are unchanged), and a run that starts from a dev server's cache no longer reads it back at the end when it did not change it.

- [#51](https://github.com/swissspidy/sandburg/pull/51) [`11e7dab`](https://github.com/swissspidy/sandburg/commit/11e7dab65a771ca033f9c626161f01f57d3ed61f) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster first installs. npm's resolution reads ahead the packuments it will ask for next (side by side, so stale cache entries are revalidated together rather than one after another), the package store unpacks each package and the WebAssembly builds and bindings are looked up as npm picks them, and a session loads npm while its browser launches.

- [#46](https://github.com/swissspidy/sandburg/pull/46) [`c0b2095`](https://github.com/swissspidy/sandburg/commit/c0b20957ae4dc6950d9dc95d4ae658ff1b15e2e5) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster runs on the host's side: the egress gateway intercepts only HTTPS, so the sandbox's own requests are no longer paused for a round trip through the host (and the browser's HTTP cache stays on); only the host server's port on `*.sandburg.localhost` bypasses the egress proxy, and the host server refuses requests from other sites. ES modules are converted without an acorn pass, the prefetch of a never-run install transforms 8 files at a time, and the host's compiles are kept on disk (`.sandburg/compiled`) for the next process.

- [#40](https://github.com/swissspidy/sandburg/pull/40) [`9433ff6`](https://github.com/swissspidy/sandburg/commit/9433ff6a207b0356bdf561e067047c4a2c0310ed) Thanks [@swissspidy](https://github.com/swissspidy)! - Less CPU per run: the browser raises V8's WebAssembly tiering budget, so the dev tools' WebAssembly builds (esbuild, rolldown, swc) optimize only code that keeps running, and spare runtime workers evaluate the runtime only when they are used, or woken by `node:wasi`.

- [#48](https://github.com/swissspidy/sandburg/pull/48) [`b337b98`](https://github.com/swissspidy/sandburg/commit/b337b98c579e6f500f1119471eb6fa3500c36b4b) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster installs: npm resolves the tree, in a worker that keeps packuments between installs, and a content-addressed store (`.sandburg/store`) unpacks each package once and hard-links it into every install, with the same files npm writes. Packages of a lockfile the install starts from, or pinned to an exact version in npm's cache, are unpacked while npm resolves; WebAssembly side installs use the same path and are kept between installs. A cold Next.js app's install phase goes from 14 s to about 6 s; installs in a batch take about half as long. The host uses more memory while installing (the resolver's worker, ~0.6 GB at its peak, which it gives back 30 s after the last install).

- [#50](https://github.com/swissspidy/sandburg/pull/50) [`adc2bfc`](https://github.com/swissspidy/sandburg/commit/adc2bfc8130543b2bee73aff9f5684f62cadcd08) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster app requests through the service worker: a response the app's server ends in one go reaches the service worker in one message instead of a start, chunks and an end, every request shares one port to the host page instead of a channel of its own, and the WebSocket shim each app page loads first is answered from the service worker's memory.

- [#45](https://github.com/swissspidy/sandburg/pull/45) [`ea9cdb6`](https://github.com/swissspidy/sandburg/commit/ea9cdb673a4ad28654166b019180ab3aac7d06e8) Thanks [@swissspidy](https://github.com/swissspidy)! - Faster runtime I/O: worker threads and child processes read their parent's preload bundle in shared memory; installed files come over a WebSocket to the host instead of a request each (requests from the browser context all pass through Playwright's routing); the page downloads a runtime's bundles while the worker starts, and a cold run loads files one at a time while its first bundle is predicted; UTF-16 writes, UTF-8 lengths and SHA hashing in the Node shims without byte-by-byte JavaScript loops.

- [#44](https://github.com/swissspidy/sandburg/pull/44) [`9d8353c`](https://github.com/swissspidy/sandburg/commit/9d8353c12f4aee36b6e2b076f431deda1def1eb9) Thanks [@swissspidy](https://github.com/swissspidy)! - Less to compile per runtime worker: the runtime's script is 0.86 MB instead of 2.8 MB. The polyfills of `node:crypto`, `node:zlib` and `node:wasi` are scripts of their own (`/__sandburg/node-crypto.js`, `node-zlib.js`, `node-wasi.js`), loaded the first time a program requires the built-in, and `node:wasi` no longer brings emnapi. Every thread and spare runtime compiles and starts faster, and a run's renderer uses less memory. A page that serves the runtime itself must serve these scripts next to `node-worker.js`.

## 0.2.0

### Minor Changes

- [#22](https://github.com/swissspidy/sandburg/pull/22) [`1228556`](https://github.com/swissspidy/sandburg/commit/1228556192150baf6c12202d72f351c4cc1ab9f7) Thanks [@swissspidy](https://github.com/swissspidy)! - `sandburg run --checks-in page` runs a checks file's code in the sandbox tab instead of Sandburg's Node process, for checks someone else wrote, such as a coding agent.
