# ADR 0004: Docker reference runtime, `sandburg compare`, and the fidelity study

- Status: Accepted (milestone 4)
- Date: 2026-09-29

## Context

The project's central question is whether in-browser runtimes can replace
per-run containers for checking generated apps, or only pre-filter them.
Answering it takes the same apps run both ways, the same checks, and a
report of where and why the two disagree.

## Decision 1: The reference is a runtime, not a separate harness

- `NodeRuntime` (`src/orchestrator/session.ts`) is the out-of-browser
  counterpart of a browser adapter: `probe`, `mount`, `install`, `start`
  (returns a loopback port), `logs` and `dispose`. `Session.run(project,
  { nodeRuntime })` drives it through the same phases, timeouts, capture,
  checks, classifier and result schema. The only difference is that the tab
  loads `http://<run>-ref.sandburg.localhost:<port>/` directly instead of a
  host page. The gateway and the dead proxy still apply: the reference
  app's page can reach only its own origin.
- `dockerReference()` (`src/reference/docker.ts`) runs one container per app
  from `node:22-slim`:
  - the project is bind-mounted,
  - `npm ci` runs when a lockfile exists, `npm install` otherwise,
  - then `npm run dev` with the framework's host and port flags,
  - a named volume holds npm's cache across runs, the "caching npm mirror"
    for the reference.

  Install and server output become the `runtime.log` artifact and
  classification evidence. When the host reaches the internet through a
  loopback proxy, the container shares the host network and gets the proxy
  and CA bundle. Otherwise it uses bridge networking with the port
  published on 127.0.0.1.
- Running dev servers, not production builds, matches what the in-browser
  runtimes do and what eval harnesses typically serve.

## Decision 2: `compare` pairs results and names causes

`compare()` (`src/compare/compare.ts`) runs a batch in the browser runtime
and a batch in the reference, then pairs the results per app. It reports:

- **pass/fail agreement** per framework and overall. Disagreements are split
  into *browser stricter* (the browser run failed and the reference passed:
  a false alarm for a pre-filter) and *browser lenient* (a missed failure),
- **causes**: the browser's classifier rule for stricter cases, and the
  seeded fault or the reference's rule for lenient ones,
- **ground-truth accuracy** of both sides, when the corpus supplies expected
  outcomes,
- **time and cost**: median and p90 run time, batch wall time, machine time
  per app at the batch's parallelism, and cost at a stated $/vCPU-hour
  (default: E2B's list price, $0.000014 per vCPU-second). Apps the reference
  could not judge (`infra`) are excluded and listed.

`sandburg compare <dir> --reference docker` writes the report as JSON and
Markdown.

## Decision 3: A synthetic, seeded corpus, labeled as such

This environment has no model access, so the corpus is generated by
`scripts/corpus/generate.ts` (deterministic, seed 1). It is not LLM output.
It mimics generated apps:

- **Scaffolds:** create-vite and create-next-app shapes (Vite + React 18/19,
  Next.js 15 App and Pages Router, Vite vanilla TypeScript).
- **Features:** 2–4 per app from 14, each with a functional check (counter,
  todo, search, tabs, form validation, modal, persistence across reload,
  converter, fetched data, dates with date-fns, a zustand store, lucide
  icons with clsx, react-router routes, a Tailwind-toggled drawer).
- **Styling:** Tailwind v4, set up as the scaffolds do today.
- **Seeded faults** in 36 of 100 apps: a logic bug the checks catch, a
  render crash, an undeclared import, a nonexistent dependency version, a
  syntax error, and a type-only error (which dev servers ignore, so the
  app should pass).

Each app's `meta.json` records the ground truth. The pipeline takes real
generated apps unchanged, and swapping in an LLM-generated corpus is the
obvious next step.

## Results

Both runs used 100 apps (34 Vite + React, 33 Next.js, 33 Vite vanilla) on a
4-vCPU container, with the browser at 4 tabs and the reference at 3
containers.

**v1: almostnode as of milestone 3.** Agreement was **77%** (Next.js 97%,
Vite + React 64.7%, Vite vanilla 69.7%). The browser matched ground truth in
80% of apps, the reference in 97%. Every disagreement had a specific cause:

| Cause | Apps | Why |
|---|---|---|
| fetched data 404s | 11 | almostnode's Vite server does not serve `public/` at `/` |
| client router shows "Not found" | 6 | the app ran under `/__virtual__/5173/`, so `BrowserRouter` saw the wrong path |
| Tailwind drawer never hides | 3 | Tailwind v4 is a Vite plugin, which almostnode does not run |
| undeclared `nanoid` import | 3 | see "Phantom dependencies" below |
| nonexistent dependency version | 2 | npm fails the install; the browser never checked the version |

**v2: the adapter fixed the first, second, third and fifth causes** (see
Decision 4). On the same corpus, agreement rose to **97%** (Next.js 100%,
Vite + React 91.2%, Vite vanilla 100%). The browser matched ground truth in
100% of apps, the reference in 97%. The three remaining disagreements are
the phantom-dependency apps below. The full reports are in
`docs/fidelity/`.

**Phantom dependencies.** `nanoid` is not declared by the three apps, but
npm hoists it into `node_modules` as a transitive dependency of Vite's
toolchain, so real Vite resolves the import. The corpus labeled these apps
"should fail", and the reference showed the label wrong. The browser
rejects the import, which is stricter than npm but matches pnpm and any
fresh install where hoisting differs. We keep this difference on purpose
and report it.

**Cost.** In v2 a browser run cost 1.8 s of machine time per app
($0.00010), with a median run of 5.3 s. A reference run cost 4.9 s
($0.00027), with a median of 12.0 s. Both were measured at their
parallelism on the same machine, so the browser is about 2.7× cheaper per
app (v1: 1.7 s vs 5.2 s). The reference was warm: the image and the npm cache
volume were already populated. Cold, `npm install` for a Next.js app takes
13–35 s.

## Decision 4: What the study changed in the almostnode adapter

- The host page moved to `/__sandburg/`, and Vite apps are served at the
  origin root. The service-worker prelude forwards the app frame's
  navigations to the dev server, so routers and absolute paths behave as
  under `vite`.
- Vite semantics added in the adapter's request wrapper: `public/` served at
  `/`, the SPA fallback to `index.html`, and extensionless imports (found in
  the pilot).
- Tailwind v4 (`@import "tailwindcss"`) is replaced by Tailwind's official
  browser build, recorded in `install.shims`.
- `install` checks that every declared version range, devDependencies
  included, matches a published version (esm.sh answers 404 otherwise). It
  fails as `app-bug`, as npm would.
- Local WebSockets (dev-server HMR) are no longer routed through Playwright,
  whose Node side cannot resolve `*.sandburg.localhost`.
- New classifier rule `compile-error` covers syntax errors reported by dev
  servers, including in runtime logs.

## Consequences

- The v1 number (77%) is the honest baseline for "almostnode as a drop-in".
  The v2 number measures the adapter after it was fixed against this same
  corpus, so it is optimistic. A fresh corpus, ideally LLM-generated, is
  needed before calling it a replacement.
- Where the browser and the reference disagree, the report names the rule
  or fault, so each disagreement is either a fix to make or a difference to
  document.
