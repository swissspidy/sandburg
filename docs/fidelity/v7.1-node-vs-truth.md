# Fidelity study v7.1: v7's corpus again, cold and warm in the same order

Run 2026-10-28 at ac9baea (main, after [ADR 0066](../adr/0066-fidelity-v7-fixes.md)'s fixes), on a
4-vCPU (Intel Xeon), 16 GB Linux machine with Node.js 24.22.2, Chromium for Playwright 1.64.1 with
its OS sandbox on (as a non-root user), 3 tabs at a time. The corpus is v7's 232 apps, unchanged,
and the answers are compared with its ground truth (`meta.expected`). Data:
[`v7.1-node-vs-truth.json`](v7.1-node-vs-truth.json) (cold) and
[`v7.1-node-vs-truth-warm.json`](v7.1-node-vs-truth-warm.json) (warm), each app with both rounds'
phases, start and end, open neighbours and the machine's CPU use while it ran.

v7 showed warm runs slower than cold for six stacks. That was its method
([ADR 0071](../adr/0071-warm-slower-than-cold.md)), so v7.1 runs the passes with
`scripts/fidelity-study.ts` (docs/fidelity/README.md, "Cold and warm passes"):

- both passes start the apps in the corpus's order, so that each app runs beside the same
  neighbours in both;
- each pass runs in a process of its own, with its batch summaries apart;
- 2 rounds of a cold pass (`.sandburg/` removed; npm's download cache warm) then a warm pass, one
  after the other. An app's time is its median over the two rounds, its answer the first round's.

## What the order does

The same warm stores and code (ac9baea), two `sandburg batch corpus --parallel 3` runs one after
the other: the first in corpus order (no earlier batch), the second longest-first from the first's
summary, as v7's warm pass ran. Median of the passing apps:

| Stack | Corpus order | Longest first | Apps >1.2× slower longest-first |
|---|---|---|---|
| Vue (Vite) | 2.1 s | 4.4 s | 6/6 |
| Static HTML | 0.9 s | 2.4 s | 7/7 |
| Express + SQLite | 2.8 s | 5.7 s | 4/6 |
| Angular 22 | 5.9 s | 7.9 s | 4/5 |
| Astro 7 | 4.8 s | 8.2 s | 5/6 |
| SvelteKit 3 | 4.3 s | 7.4 s | 4/6 |
| Next.js 15 | 8.0 s | 7.9 s | 3/23 |
| Wall time | 565 s | 559 s | |

Longest first starts the apps that wait in failing checks first, then the rest by their run's
length, so the fast stacks' passing apps start last (static HTML's 7 at positions 192 and 227–232 of 232, Vue's 6 at 172–211) and run beside other
passing apps, each busy in its own checks, where in corpus order they run beside apps that wait
in a failing assertion. The number of open neighbours is alike (static HTML 4.6 against 5.0); the
time goes to the checks phase (static HTML 0.45 → 1.70 s, Vue 0.58 → 1.69 s) and to ready and
start. The batch's wall time does not change: the order moves time between apps.
