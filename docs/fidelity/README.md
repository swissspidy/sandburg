# Fidelity studies

almostnode, measured in v1 and v2, was removed in [ADR 0013](../adr/0013-runtime-consolidation.md); v3 measures its replacement (`--runtime auto`), and v4 the node runtime alone ([ADR 0014](../adr/0014-node-runtime-only.md)); v5 and v6 measure the speed work since, and v7 the frameworks added since, on a corpus of 232 apps; v7.1 runs v7's corpus again after its fixes, with cold and warm passes in the same order.

Each study runs the same apps (`corpus/`, generated by
`scripts/corpus/generate.ts` with seed 1) in the browser runtime, and v1 and v2
also in the Docker reference, with identical checks. v1–v6 ran apps 000–099
(Vite, Vite + React, Next.js); v7 added 12 apps each for SvelteKit, Angular,
Nuxt, Astro, SolidStart, React Router, Vue, Svelte, Lit, Express + SQLite and
static HTML (100–231), and leaves 000–099 unchanged. For the method and the caveats, see
[ADR 0004](../adr/0004-docker-reference-and-fidelity-study.md).

|---|---|---|---|---|---|

Caveats:
- The corpus is synthetic, and v2's adapter fixes were made against this
  same corpus. Treat v1 as the drop-in baseline and v2 as an upper bound
  until a fresh, LLM-generated corpus is run.
- The reference's three "misses" against ground truth are phantom
  dependencies (`nanoid` is hoisted by npm), not reference bugs. The
  corpus's labels were wrong for those three apps (054, 078, 084) until v7,
  which labels them `pass`.

To reproduce, generate the corpus first:

```sh
node scripts/corpus/generate.ts corpus 232 1    # v1–v6 ran the first 100: count 100
```

v1 and v2 (almostnode, which no longer exists, against the Docker reference):

```sh
node bin/sandburg.js compare corpus --reference docker --parallel 4 --report docs/fidelity/vN-almostnode-vs-docker
```

v3 to v7 (against ground truth; v3's `--runtime auto` no longer exists): run the batch, then compare each run's
status with the app's `meta.expected` (`corpus/<app>/meta.json`):

```sh
mkdir -p .sandburg/study && node bin/sandburg.js batch corpus --parallel 3 --out .sandburg/study --json > .sandburg/study/batch.json
```

With Docker, `compare corpus --reference docker` also reports agreement with the reference.

### Cold and warm passes (from v7.1 on)

v7's warm medians for Vue, static HTML, Express + SQLite, Angular, Astro and SvelteKit were higher
than its cold ones. That was the method, not Sandburg ([ADR 0071](../adr/0071-warm-slower-than-cold.md)):
measured in the same order, warm is faster than cold on every stack but static HTML, which has nothing
to install and is the same either way (in v7.1, at parallel 3, every stack is faster warm). Run the passes with `scripts/fidelity-study.ts`, which:

- starts the apps in the corpus's order in both passes (`longestFirst: false`): the same start
  order, though not the same overlap, since a cold pass's runs are longer. A batch otherwise starts
  first the apps that took longest in its earlier batches (`.sandburg/batches`). Only the warm pass
  has an earlier batch, so v7's warm pass ran its fast apps last, side by side, beside other warm
  apps;
- keeps each pass's batch summaries apart, and runs each pass in a process of its own;
- with `--rounds n`, runs n cold/warm pairs one after the other. An app's time in a pass is the
  median of its passing rounds, and the table's medians are over the apps that pass in both passes;
- records each run's phases, start and end, its mean number of open neighbours and the machine's
  CPU use while it ran;
- keeps each pass as it ends (`<out>-passes.jsonl`), with the corpus, apps, `--parallel`,
  `--only` and commit it ran with: the same command again goes on from there, one with other
  arguments or at another commit is refused, and `--report` renders the table and the JSON from
  the kept passes without running anything (every round kept, and the apps' labels as the passes
  ran them). It refuses an `--out` under `.sandburg/`, and a run with
  `SANDBURG_INSTALL_DIR` or `NODE_COMPILE_CACHE` set (stores a cold pass would not remove).

```sh
node scripts/corpus/generate.ts corpus 232 1
node scripts/fidelity-study.ts corpus --parallel 3 --rounds 2 --out docs/fidelity/vN-node-vs-truth
```

How to read the times:

- At `--parallel` above 1, an app's time is mostly what runs beside it: 2–3× its time alone. The
  same warm batch run longest-first instead of in corpus order took the same wall time, and Vue's
  median went from 2.1 to 4.4 s, static HTML's from 0.9 to 2.4 s (v7.1, "What the order does").
  Compare cold with warm per app at `--parallel 1`, or where the `cpu` of both runs is alike. The
  batch's wall time is the measure of the parallel pass.
- "Cold" is cold for Sandburg's stores only: npm's own download cache and the OS's page cache stay
  warm, the batch warms up
  the Vite, Vite + React and Next.js stacks first, and only a stack's first app installs from
  scratch (its later apps install from the store the first one filled).
- A warm batch's first app is its session's first tab; a cold batch's first app runs after the
  warm-ups, in a browser that has already run apps (static HTML's first app: 2.0 s cold, 2.3 s warm,
  n=8).
